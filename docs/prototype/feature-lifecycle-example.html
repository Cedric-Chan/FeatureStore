5 例归纳 · 模型最终收敛

关键 finding

  • Pre-compute Source 不止流式：可能是 Flink 流（例 1/2）、Spark T+1 批刷新（例 5）、或没有（例 3/4）。术语统一为 "Pre-compute Source"，弃用"Stream Stage"。
  • Hive 物化 feature 表双重身份：既是 Source Pipeline 的 output，又是 Feature Source 的 query interface——lineage 图上是同节点两面。
  • Kafka / Hive ODS 不进 FS：它们只在 Source Pipeline 里出现；FG 不直接 query。
  • Transformation demote 合理：5 例均不需要独立 Transformation entity——加工逻辑要么在上游 Spark/Flink（属 SP），要么在 Serving Canvas 节点（属 FG.Feature Logic）。
  • 例 3 揭示 Compute Template 价值：200 features 共享一段 Python 算子——若离线 SP 和在线 Canvas 引用同一份代码，consistency 几乎免费。建议 v2 引入 Compute Template（库性质，非治理层级）。
  • 例 5 的 Pre-compute 是批刷新：证明"实时 vs 离线"和"流 vs 批"是两个独立轴。
  • "千级 features per FG" 主要发生在"同源批量解析"场景（例 3 类）。建议 auto-generate Features + exposed 标签 + Feature Section 分组。

还需要你拍板的 3 件事

  1. 例 3 的 Compute Template 要不要 v2 一起做？
    做 → consistency "一份代码 = 一致"，工程量 +30%
    不做 → 等用户痛了再加
  2. "Pre-compute Source" 替代 "Stream Stage"，OK？
    OK → 文档里所有"流式"统一改成"Pre-compute"，并明确批刷新也算
  3. Hive Materialized Table 并入 FS（v1 FS 不含 Hive），结构性变化，OK？
    OK → Source Type 枚举加 HIVE_TABLE；反对 → Hive 单独成 entity（层级会乱）
